# PillCheck

사진 한 장으로 여러 알약을 찾아 이름을 알려 주고, 함께 먹으면 안 되는 약을 쉬운 말로 알려 주는 AI 서비스입니다.

- 소개 페이지: https://quad0623-ctrl.github.io/pillcheck-showcase/
- 팀: 계명대학교 D5 청년인재 혁신아카데미 ABB 과정 · SD팀
  - Dagmawe ([@Dagim7](https://github.com/Dagim7)): AI 엔진. 모델 설계·학습, 앱 연동·추론 서버
  - 유시안 ([@quad0623-ctrl](https://github.com/quad0623-ctrl)): 플랫폼·프로덕트. 학습 인프라, 앱 개발·디자인·배포

이 저장소는 소개 페이지만 담고 있습니다. 앱과 서버 코드는 비공개입니다.

## 무엇을 하나요

1. 여러 알약을 한 장에 찍으면 알약마다 위치를 찾아 번호를 붙입니다.
2. 사진 분류 모델 2종, 각인(알약 글자) 판독, 식약처 낱알식별 목록을 서로 맞춰 봅니다. **2가지 이상이 같은 약을 가리킬 때만** 이름을 "확인됨"으로 보여 줍니다.
3. 찾은 약은 식약처 DUR로 병용금기 등 8개 항목을 조회해 쉬운 말로 알려 줍니다. 조회 결과가 없으면 "안전합니다"가 아니라 "등록된 주의사항이 없습니다"라고 씁니다.

| 범위 | 내용 |
|---|---|
| 사진으로 식별 | 4,519종 (AI Hub 경구약제 이미지로 학습) |
| 각인 검색 | 식약처 낱알식별 목록 25,000여 종 |
| 처리 속도 | 알약 하나에 1~1.5초 (서버 RTX 2060) |

## 개발 과정 (2026년 7월 ~ 10월)

### 1. 주제 정하기 (7월)
알약 식별과 CT 판독 보조, 두 아이디어를 놓고 고민했습니다. 결과물로 직접 보여 줄 수 있고, 공공데이터(AI Hub 경구약제 이미지, 식약처 DUR)를 바로 쓸 수 있는 알약 식별을 골랐습니다. 7월 16일 산학 프로젝트 계획서를 냈습니다.

### 2. 30종으로 작게 시작 (8월 초)
원본 데이터는 5,000종, 수 TB 규모였습니다. 그래서 일반의약품 가운데 모양과 색이 뚜렷이 다른 30종(35,856장, 약 6GB)으로 먼저 파이프라인을 만들었습니다.
- 엑셀 목록, 라벨, 이미지를 교차 검증해 30종이 모두 일치하는 것을 확인했습니다.
- 읽을 수 없는 이미지 1장을 지우고 80/20으로 나눴습니다(seed 42, 재현 가능한 목록 저장).
- 배경이 메타데이터와 다르게 실제로는 여러 종류여서, 검은 배경을 가정한 잘라내기는 보류했습니다.

### 3. 전환점: 99.97%를 의심하다 (8월 중순)
첫 CNN이 검증 정확도 99.97%를 냈습니다. 원인을 찾아보니, 한 알약을 회전 장비로 찍은 거의 같은 사진들이 학습과 검증에 섞여 있었습니다(이웃 사진 픽셀 차이 0.6%, 504개 촬영 세션 모두 겹침).
- **촬영 세션 단위로 다시 나눠** 겹침을 0으로 만들었습니다.
- 이때부터 "외운 점수가 아니라 정직한 점수"를 기준으로 삼았습니다.

### 4. 전환점: 알약부터 찾기 (8월 말)
알약은 사진의 7%만 차지해서 모델이 배경 밝기를 외우고 있었습니다.
- 알약을 먼저 찾는 **검출기**와 약을 맞히는 **분류기**, 두 단계로 바꿨습니다(검출 IoU 0.944, 분류 96.08%).
- 데이터와 학습을 Elice Cloud 버킷과 GPU로 옮겼습니다.

### 5. 글자로 한 번 더 확인 (9월 초)
- 전이학습(EfficientNet-B0 98.85%)과 직접 만든 CNN 개선판(99.22%)을 비교했습니다.
- 생김새가 비슷한 약끼리 헷갈려서, 합성 이미지로 학습한 **각인 판독기**를 직접 만들었습니다(30종 기준 95%, 범용 OCR 40.5%).
- 여러 모델 중 2개 이상이 일치할 때만 결과를 내는 원칙을 세웠습니다.

### 6. 전환점: 휴대폰 사진의 벽 (9월 중순)
스튜디오 사진에서 99%가 넘던 모델이 실제 휴대폰 사진에서는 크게 틀렸습니다.
- 검출기 출력층 문제와 정규화 불일치를 고쳤습니다.
- 촬영 가이드(밝은 무지 배경, 가까이, 바로 위에서)를 만들었습니다.
- 확실하지 않으면 이름을 단정하지 않고 다시 찍어 달라고 하도록 바꿨습니다.

### 7. 30종에서 4,519종으로 (9월 중순 ~ 말)
- AI Hub 원본 91개 묶음(약 3.7TB)을 로컬을 거치지 않고 클라우드로 바로 옮겼습니다. 알약 크롭 약 261만 장을 만들었고, 조합약 라벨 오류는 규칙으로 걸렀습니다.
- 학습: A100 80GB × 2, 2-GPU 분산 학습.
  - 검출기 PillNet: mAP50 0.985
  - 분류기 CNN16 / EfficientNet-B0: 4,519종
  - 각인 OCR 2종: 정확 일치 99.5% / 97.4%
- 사진이 없는 약까지 다루기 위해 식약처 낱알식별 목록 25,000여 종의 각인·모양·색 검색을 붙였습니다. 이 경우는 항상 "후보"로만 안내합니다.
- 식약처 DUR 연동, 여러 알약 동시 검출, FastAPI 추론 서버를 만들었습니다.

### 8. 앱 완성 (9월 말 ~ 10월 초)
- Flutter 앱을 1.0에서 1.2.x까지 다듬어 Google Play 비공개 테스트에 제출했습니다(9월 23일 첫 제출).
- 촬영 코치, 분석 진행 표시, 내 사진과 공식 사진 비교, 다국어(한·영·일·중), 웹 버전을 더했습니다.
- 코드 점검으로 서버와 앱의 버그를 정리했습니다.
- 서버 API가 바뀌는 동안에도 심사 중인 빌드가 계속 동작하도록 이전 API를 유지했습니다.

### 9. 발표와 전시 (10월)
- 산학 프로젝트 평가 발표에서 라이브로 시연했습니다.
- 2026년 10월 21일 대구·경북 초광역 이음 모빌리티 취업박람회(EXCO)에 부스로 전시합니다.

## AI와 함께 일한 방식

둘이서 4개월 만에 30종 실험에서 4,519종 앱까지 올 수 있었던 데는 AI 코딩 도구의 힘이 컸습니다. 코드와 문서는 AI가 초안을 많이 썼지만, **무엇을 할지 정하고 결과를 검증하는 일은 사람이** 했습니다.

| 시기 | 도구 | 쓴 곳 |
|---|---|---|
| 8월 ~ 9월 | Cursor (Agent·Plan 모드) | 데이터 확보·검증, 전처리, 모델 학습 노트북, 첫 Flutter 앱, Play 제출 준비 |
| 10월 | Claude Code | 앱 화면 개편과 테스트, 코드 점검 보고서, 발표 예상 질문, 전시 포스터와 소개 페이지 |
| 서버 쪽 | 팀원의 LLM | 요청서를 서버 PC의 LLM에 넣어 정해진 형식으로 답장받는 방식으로 협업 |

**사람이 정하고 검증한 것**
- 주제, 약 30종 선정, 클라우드 GPU 선택, 무료·공익 방향
- 99.97%를 의심하고 평가 방식(촬영 세션 단위 분할)을 다시 설계
- 자체 CNN 개선과 각인 판독으로 가는 모델 방향
- 화면 구성과 점수 표시 같은 디자인 결정. AI 추천과 다르게 고른 것도 있습니다.
- 파일 삭제처럼 되돌리기 어려운 작업은 직접 승인

**AI의 도움을 받은 것**
- 데이터 검증·전처리 스크립트, 학습 노트북 코드
- 오류 로그를 붙여 넣으며 하는 디버깅(클라우드 업로드, 학습 환경, 앱 빌드)
- Flutter 앱 코드, 테스트, APK·AAB 빌드
- 보고서, 앱 점검 보고서, 발표 예상 질문, 스토어 정책 답변 초안
- 팀원을 위한 번역과 다국어(한국어·영어·암하라어) 문서

**일하는 방식**
1. **먼저 검증을 시킨다.** 엑셀·라벨·이미지 대조, 배경색 픽셀 감사를 AI에게 맡겨 "검은 배경"이라는 메타데이터가 실제와 다르다는 걸 찾았습니다. 결과에는 "정말 맞나요?"를 다시 물었습니다.
2. **계획은 먼저, 실행은 승인 후.** 계획 모드로 단계를 세운 뒤 승인하고 실행했습니다. "스크립트만 쓰고 멈춰"처럼 범위를 좁혀서 맡겼습니다.
3. **언어의 벽을 AI로 넘는다.** 외국인 팀원과 일하며 번역과 다국어 가이드를 만들고, 팀원의 LLM이 그대로 읽고 답할 수 있는 요청서 형식을 썼습니다.
4. **기록과 재현성을 지킨다.** 노트북에 번호를 매겨 실험을 관리하고, 실수로 두 번 돌린 학습은 처음부터 다시 실행했습니다.

Cursor에서 PillCheck 관련 지시는 약 570건이었습니다(대략). 많은 순서로 학습 코드·디버깅 약 170, 앱 개발·빌드 약 90, 데이터 확보·업로드 약 80, 보고서·문서 약 50, 팀원 소통·번역 약 40, 스토어 심사 준비 약 40입니다.

## 배운 점
- **높은 점수는 먼저 의심합니다.** 99.97%의 원인은 데이터 누수였습니다.
- **스튜디오 정확도는 현실이 아닙니다.** 그래서 모든 성능 수치에 측정 조건을 적습니다. 위 정확도는 학습에 쓰지 않은 AI Hub 촬영 사진 기준이고, 실제 휴대폰 사진 성능은 검증 중입니다.
- **모르면 모른다고 말합니다.** 건강과 관련된 서비스이므로 틀린 이름보다 "다시 찍어 주세요"가 안전합니다.
